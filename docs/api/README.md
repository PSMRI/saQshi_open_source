# SaQshi API Developer Documentation

Version: 1.1
Updated: 2026-08-26

This documentation explains the API layer for developers who need to maintain,
debug, or extend SaQshi. It intentionally documents both the HTTP contract and
the implementation path behind each endpoint.

## API Access Boundary

Most SaQshi APIs are authenticated application APIs. They must derive user, role and facility scope from the active server-side session and must not trust a client-supplied facility ID, role or user ID as an authorization decision.

The deliberately public endpoints are limited to functions needed before login or to render public branding. Current examples include:

| Endpoint | Method | Purpose | Public-data limit |
|---|---|---|---|
| `/api/auth/v1/captcha.php` | `GET` | Returns the pre-login text captcha challenge. | No user/session or deployment-secret data. Unsupported methods are rejected. |
| `/api/config/v1/public_deployment.php` | `GET` | Supplies public profile code, name, labels, branding and content for the landing page. | Never add credentials, internal hosts, storage paths, user data, role data or operational configuration. |

All other endpoints must be treated as protected unless their implementation and security review explicitly establish a narrower public contract. Public availability is not authorization to expose deployment data.

The profile-branding endpoint is consumed by the root landing page: Healthcare remains on `index.html`; Education redirects to `education-index.html`. This endpoint is intentionally narrower than the authenticated deployment configuration API.

## Request lifecycle

```text
Client request
  -> public API entry point / route dispatcher
  -> bootstrap/auth include
  -> method and input validation
  -> service class and/or prepared database query
  -> Response helper JSON envelope
```

Most endpoint files include either `api/auth_api.php` or a module-specific
bootstrap file. These files establish the common runtime, session context,
authentication and response utilities before business logic executes.

## Conventions used in this guide

- **Source** is the repository-relative PHP file that implements the endpoint.
- **URL** is inferred from the file path unless a router or caller overrides it.
- **Session-derived input** means the value is obtained from `SessionManager`,
  rather than trusted from the request body.
- **Why it exists** describes the business responsibility, not merely the code.
- Endpoint documentation distinguishes public endpoints from internal helpers
  such as `_common.php` and `_bootstrap.php`.

## Safe extension checklist

1. Reuse the module's bootstrap/authentication pattern.
2. Require and validate the expected HTTP method before processing input.
3. Obtain facility/user identity from the session where authorization requires it.
4. Use prepared statements for every database value.
5. Keep response envelopes consistent through `Response` helpers.
6. Record any needed audit/history data before changing a lifecycle state.
7. Add the new endpoint to this documentation and to the Postman collection.

8. Update `openapi.yaml` when the endpoint is part of a supported external contract.
9. Add a positive and a negative authorization test, including a cross-facility/scope test where applicable.
10. For any new public endpoint, document its data classification, cache behavior, permitted method, rate/abuse controls and expected response headers before release.

## Local Verification

Run focused checks from the repository root after API changes:

```powershell
php tools/json_syntax_check.php
php tools/php_style_check.php
php tools/run_unit_tests.php
```

For a local public-route smoke test, confirm the public branding endpoint returns HTTP 200 and that an unsupported captcha method returns HTTP 405. Use an authenticated test session and least-privilege role accounts for protected endpoint checks. Do not run active security attacks against a shared or production environment without written approval.

## Response and Error Handling

Use the shared `Response` and `Security` helpers rather than emitting ad-hoc JSON or raw PHP/database errors. A production response must preserve a stable, documented envelope while returning only safe error detail to the browser. Capture diagnostic context through the approved server-side logging/audit mechanisms, which redact sensitive values; never return secrets, passwords, tokens, session IDs, SQL text or filesystem paths in an API response.

## Documentation Maintenance

When changing API source, update the endpoint inventory, applicable module guide, Postman collection, OpenAPI contract where relevant and security/testing evidence in the same change. Regenerate the source reference only after reviewing the generated output to ensure it contains no secrets, local paths or runtime data.

The assessment module also provides a facility-scoped FHIR R4 `MeasureReport`
export. Its machine-readable contract is included in `openapi.yaml` and its
request is included in the Postman collection.
